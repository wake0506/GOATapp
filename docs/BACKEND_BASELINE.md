# Backend Baseline

Branch baseline: `feature/backend-production-sync`, based on the reverted phase-one head.

## Current Client Tables

`CloudSyncService` currently reads and writes these Supabase tables:

- `user_profiles`: profile, targets, `current_weight`, and the legacy `training_data` JSON payload.
- `food_dictionary`: user-created and AI-created food definitions.
- `diet_logs`: consumed food records.
- `exercise_logs`: timed exercise records.
- `daily_tracking`: compatibility date rows containing `water_ml` and `weight_kg`.
- `chat_history`: referenced by the coach page; it is read/written by the client but is not yet part of the versioned sync protocol.

The client also references the `delete_user` RPC and `chat_history` from the assistant page. The current sync service does not synchronize chat history.

## Missing Cloud Entities

The client already stores individual `water_intake_records` locally, but the current cloud sync explicitly leaves those records local. There is no versioned `body_weight_logs`, `training_sessions`, `sync_tombstones`, `client_operations`, or `ai_usage_daily` client contract in the baseline.

## Compatibility Risks

- Existing profile and tracking columns are already used by the client and must remain readable.
- `user_profiles.training_data` is an atomic JSON payload and must remain during the training migration.
- `daily_tracking.water_ml` is a compatibility aggregate; individual water records are the source of truth locally.
- Existing IDs are strings generated by the Flutter client. New migrations therefore use text-compatible IDs where existing tables may already contain client IDs.
- The current cloud sync performs full-table reads and snapshot upserts. Incremental reads must be feature-gated until the migration is deployed remotely.
- The current client has explicit pending deletion sets. They remain readable while the durable operation queue and tombstone model are introduced.

## Data To Preserve

- All namespaced local snapshots, including guest data before authenticated upload.
- `user_profiles.training_data`.
- Existing food, diet, exercise, daily tracking, weight, and training IDs.
- Legacy daily water totals, migrated to stable `legacy_water_YYYY-MM-DD` detail records without inventing a real drinking time.
- Current profile weight and historical daily weights without changing numeric values.

## Tables And Columns That Must Not Be Destructively Removed

- `user_profiles.training_data`
- `user_profiles.current_weight`
- `daily_tracking.water_ml`
- `daily_tracking.weight_kg`
- Existing IDs, `date` fields, nutrition columns, and legacy water compatibility fields.

## Production Boundary

This phase creates local migrations and client adapters only. `supabase db push`, `supabase secrets set`, and `supabase functions deploy` are intentionally not executed by Codex in this phase.
